# 开发规范

## 1. 适用范围

本规范适用于 Marine Insight 的 C#、Razor、JavaScript 互操作、数据库迁移、测试、配置和 Markdown 文档。任何例外应在 Pull Request 中说明原因和影响。

## 2. 开发环境

| 工具 | 基线版本 | 说明 |
| --- | --- | --- |
| .NET SDK | 9.x | 使用 `global.json` 固定功能带 |
| IDE | Visual Studio 2022 / Rider / VS Code | 启用 EditorConfig 和分析器 |
| PostgreSQL | 16+ | 集成测试与生产基线 |
| SQLite | 当前稳定版 | 本地快速开发，不替代 PostgreSQL 测试 |
| Redis | 7+（可选） | 多实例缓存场景 |
| Docker Engine | 26+ | 本地与生产容器化 |
| PowerShell | 7+ 推荐 | Windows 自动化脚本 |

## 3. 解决方案结构

```text
src/
├── MarineInsight.Domain/          # 领域模型、规则、评分
├── MarineInsight.Application/     # 用例、端口、DTO、验证
├── MarineInsight.Infrastructure/  # EF Core、Provider、缓存、AI
├── MarineInsight.Web/             # Blazor、API、认证、Composition Root
└── MarineInsight.Worker/          # 可选后台任务
tests/
├── MarineInsight.Domain.Tests/
├── MarineInsight.Application.Tests/
├── MarineInsight.Infrastructure.Tests/
└── MarineInsight.Web.Tests/
```

依赖方向固定为 Web/Infrastructure -> Application -> Domain。Domain 不引用 EF Core、HttpClient、Blazor、供应商 SDK 或配置系统。

## 4. C# 编码规范

- 启用 Nullable Reference Types、Implicit Usings 和 .NET 分析器。
- 公共 API 使用清晰的英文领域命名；用户文本使用资源文件或集中模板。
- 时间使用 `DateTimeOffset`；内部存储 UTC，禁止使用语义不明的 `DateTime.Now`。
- 核心单位在命名中明确，例如 `WindSpeedMs`、`WaveHeightM`、`PeriodS`。
- 缺失指标使用可空值和质量状态，不使用 0、`double.NaN` 或魔法数。
- 阈值、错误码和规则代码集中版本化，不散落在组件或 Controller。
- 异步方法以 `Async` 结尾，接受并传递 `CancellationToken`，禁止 `.Result`/`.Wait()`。
- 捕获异常时保留原异常；禁止空 catch、无界重试和以异常控制正常业务流程。
- 集合参数优先使用只读接口；领域对象通过方法维护不变式，不公开任意 setter。

## 5. 注释与文档

- 注释解释业务原因、单位语义、第三方差异和保守规则，不复述语法。
- 长周期涌浪、方向语义、缓存降级、算法边界等易误解逻辑必须有简短注释。
- 简单赋值、明显条件和标准 CRUD 不添加无效注释。
- 公共扩展点和复杂算法使用 XML 文档或对应设计文档链接。
- 每次新增或修改文本文件时，除 JSON/YAML 等现代配置文件外，统一使用 UTF-8 with BOM 和 CRLF。

## 6. Razor 与前端规范

- 页面组件只编排用例和 ViewModel，不直接访问 `DbContext` 或 Provider。
- 复杂组件拆分 `.razor`、`.razor.cs` 和 `.razor.css`，简单展示组件保持单文件。
- 使用 Lucide/MudBlazor 现有图标，不手写重复 SVG。
- 风险信息同时提供文字和图标，不能只依赖颜色。
- 所有异步视图具备加载、空、部分数据、错误和取消状态。
- JS 互操作集中封装 ES Module，组件释放时销毁地图/图表实例。
- 360px 及以上常见视口不得出现文本、按钮、图表和导航重叠。

## 7. 数据与 Provider 规范

- 第三方 DTO 只能存在于 Infrastructure Provider 目录。
- 每个字段映射必须明确原单位、目标单位、时间语义和方向语义。
- 原始缺失不得补 0；异常值先标记质量状态，再由领域决定是否可分析。
- 外部 API 使用 `IHttpClientFactory`、韧性处理、超时和结构化日志。
- API Key 不进入源码、测试快照、日志和镜像。

## 8. 数据库规范

- EF Core 配置使用 `IEntityTypeConfiguration<T>`，不在实体类堆积存储细节。
- 迁移命名表达业务变化，例如 `AddForecastQualityFlags`。
- 生产迁移生成 SQL 评审，不在应用多实例启动时并发自动迁移。
- 查询默认投影所需字段并使用异步 API；只读查询使用 `AsNoTracking()`。
- SQLite 测试通过不代表 PostgreSQL 行为正确，Provider 特性必须用真实 PostgreSQL 验证。

## 9. Git 与提交

分支建议：

| 分支 | 用途 | 生命周期 |
| --- | --- | --- |
| `main` | 可发布主线 | 长期 |
| `feature/<topic>` | 功能开发 | 合并后删除 |
| `fix/<topic>` | 缺陷修复 | 合并后删除 |
| `docs/<topic>` | 文档更新 | 合并后删除 |

提交格式：

```text
<type>(<scope>): <summary>
```

常用 `type`：`feat`、`fix`、`docs`、`test`、`refactor`、`perf`、`build`、`chore`。示例：`feat(analysis): add long-period swell shore risk rule`。

## 10. Pull Request 与评审

PR 必须包含：目的、范围、关键决策、风险、验证命令和文档影响。UI 变更附桌面/移动关键截图，算法变更附边界样本和版本变化。

评审重点：

- 风险规则是否保守、可解释且有边界测试。
- Provider 缺失、单位、时间和方向是否正确处理。
- 是否存在越权、密钥泄露、无限重试或同步阻塞。
- 是否破坏历史结果可追溯和算法版本语义。
- UI 是否存在重叠、仅颜色表达或错误状态缺失。

## 11. 测试规范

- 测试命名建议：`Method_Scenario_ExpectedResult`。
- 领域规则采用表驱动测试覆盖阈值前、等于阈值和阈值后。
- Provider 使用录制/人工构造契约样本，不在单元测试调用真实付费 API。
- 集成测试使用隔离 PostgreSQL 容器或测试数据库。
- E2E 覆盖真实主流程、移动视口和故障降级。
- 缺陷修复必须先添加可复现测试，或在 PR 中说明无法自动化的原因。

## 12. 配置与密钥

- `appsettings.json` 只保存非敏感默认值。
- 本地使用 User Secrets 或未提交的环境文件；生产使用环境变量/Secret 服务。
- Options 类启用启动时验证，关键 Provider 配置无效时健康检查为不就绪。
- 配置键、环境变量和部署文档同步维护。

## 13. Definition of Done

1. 功能满足 PRD/SRS 验收标准。
2. 代码通过格式、分析器、构建和相关自动化测试。
3. 关键失败、缺失数据、取消和权限路径已覆盖。
4. UI 在目标桌面/移动视口完成截图检查。
5. 日志不含敏感信息，指标和健康检查满足运维需要。
6. API、算法、数据库、部署或用户行为变化已同步文档。
7. 本次修改的文本文件符合 UTF-8 BOM 与 CRLF 约定。
