# 缓存设计

## 1. 设计目标

- 降低 Open-Meteo、Stormglass、WorldTides 等外部 Provider 的调用量、延迟和配额成本。
- 在短时外部故障时提供带明确时效标记的可用降级结果。
- 避免同一地点和时间范围的并发请求造成缓存击穿。
- 保证算法、Provider 和标准化版本变化后不会读取语义过期的数据。

缓存不是事实唯一来源，不得把缓存写入成功当作业务事务完成条件。

## 2. 缓存分层

| 层级 | 技术 | 数据 | 适用场景 |
| --- | --- | --- | --- |
| L1 | `IMemoryCache` | 热点地点、短期响应、小型配置 | 单实例低延迟 |
| L2 | Redis（可选） | 标准预报、分析响应、分布式锁 | 多实例共享和容灾 |
| 持久层 | PostgreSQL | 预报批次、分析结果、算法版本 | 可追溯和恢复 |
| 客户端 | ETag/浏览器缓存 | 不含敏感信息的只读响应 | 减少重复传输 |

Redis 不可用时，系统降级到 L1 + PostgreSQL/Provider，不能使核心查询完全中断。

当前 .NET 实现先落地 L1；`IForecastBatchCache` 是 Application 端口，后续 Redis 适配器可复用相同键和结果语义，不把 Redis 作为当前 MVP 的运行前置条件。

## 3. 缓存对象与 TTL

| 对象 | Key 示例 | 新鲜 TTL | 过期降级窗口 |
| --- | --- | --- | --- |
| 地点搜索 | `mi:{env}:location:search:{queryHash}:v1` | 24 小时 | 7 天 |
| 标准预报 | `mi:{env}:forecast:{provider}:{model}:{grid}:{range}:{normalizerVer}` | 10-30 分钟 | 2 小时，可配置 |
| 分析结果 | `mi:{env}:analysis:{sourceSetHash}:{algorithmVer}:{activitySet}` | 取决于最短来源新鲜期 | 跟随各来源批次 |
| AI 摘要 | `mi:{env}:explanation:{analysisId}:{promptVer}:{modelVer}:{locale}` | 24 小时 | 不使用过期降级，改用规则模板 |
| 算法配置 | `mi:{env}:algorithm:published` | 5 分钟 | 数据库回源 |
| 用户设置 | `mi:{env}:user-setting:{userId}:v1` | 15 分钟 | 数据库回源 |
| 空地点结果 | `mi:{env}:location:miss:{queryHash}` | 1 分钟 | 无 |

TTL 必须遵守第三方数据授权和模型更新频率。缓存响应保留原 `fetchedAt`，不能刷新成当前时间。

## 4. Key 规范

```text
mi:{environment}:{module}:{provider-or-scope}:{identity}:{semantic-version}
```

- 坐标按可配置网格精度归一化，避免相邻浮点值产生大量 Key。
- 时间范围按 UTC 小时边界归一化。
- Key 不包含邮箱、令牌、API Key 或可直接识别个人的信息。
- 序列化格式升级必须修改语义版本，禁止静默复用旧值。

当前标准预报键由 `ForecastCacheKey` 生成：`environment`、数据域、Provider、模型、按配置精度归一化的坐标、UTC 小时起点、24/72/168 小时范围和 `normalizerVersion` 均参与键值。

## 5. 读写策略

### 5.1 标准预报

采用 Cache-Aside：

1. 查 L1；未命中查 L2。
2. L2 命中时回填 L1。
3. 均未命中时获取单航班锁，仅一个请求回源 Provider。
4. 标准化和质量校验通过后，先形成业务结果，再尽力写 L2/L1。
5. 锁等待方短暂等待缓存，超时后返回可用旧值或明确错误。

当前 `ForecastBatchCacheCoordinator` 在 L1 未命中或已进入过期窗口时执行单航班刷新；等待方只取消自己的等待，不取消共享刷新。Provider 成功后回填 L1，ProviderException 且旧值仍在降级窗口内时返回 `StaleCache`。

缓存适配器将后端连接、序列化或 Redis 故障包装为 `CacheUnavailableException`；协调器把读取故障当作未命中、把写入故障当作尽力失败，不让缓存故障阻断 Provider 或持久层结果。

### 5.2 分析结果

分析缓存由 `sourceBatchSetHash + sourceSelectionPolicy + algorithmVersion + activitySet` 决定。单位偏好不进入领域分析缓存，展示层执行换算，减少重复数据。Weather、Marine 和 Tide 任一被替换时都必须生成新 Key。

### 5.3 写数据

收藏、设置和算法发布以数据库为准。事务提交后删除或更新缓存；失败时记录告警，不回滚已成功的数据库事务。

## 6. 失效与一致性

- 新预报批次产生后无需全量删除旧批次缓存，新查询通过最新批次键自然切换。
- 算法发布后切换 `published` 指针；旧分析缓存因版本不同自然失效。
- 用户设置更新后删除对应用户 Key。
- Provider/标准化映射变化时提升版本段，避免读取旧语义数据。
- 不使用大范围通配符扫描删除生产 Redis Key。

## 7. 穿透、击穿与雪崩防护

- 穿透：输入校验、短 TTL 空结果、地点搜索最小字符数和限流。
- 击穿：单航班锁、热点 L1、提前刷新和有限等待。
- 雪崩：TTL 加 5%-15% 随机抖动；不同模块错峰过期。
- Provider 配额耗尽：停止新回源，优先返回仍在降级窗口内的缓存并标记 `Stale`。

## 8. Stale-If-Error

只有在以下条件同时满足时才返回旧预报：

- Provider 调用失败或熔断。
- 缓存年龄未超过最大降级窗口。
- 关键字段质量仍可识别。
- 响应显著显示“缓存数据”、实际时间和低置信度原因。

超过窗口或存在雷暴等时效敏感风险缺失时，不返回乐观旧结论，而返回 `ProviderUnavailable` 或 `Unknown`。

缓存降级不会修改 `ForecastBatch.FetchedAtUtc` 或任何指标值。领域模型会把批次、点位和指标来源的时效标记统一为 `Stale`，并增加 `StaleData` 标志；原有完整度、缺失指标和无效/未知状态继续保留。

## 9. 容量规划

初始按 1,000 个热点网格、每个 168 个小时点估算。预报缓存只保存必要标准字段，避免重复保存原始 Provider 负载。Redis 设置 `maxmemory` 和明确淘汰策略，持久业务数据不依赖 Redis AOF/RDB。

| 指标 | 目标/告警 |
| --- | --- |
| 预报缓存命中率 | 目标 >= 70%，低于 50% 持续告警 |
| Redis 内存使用率 | >= 75% 预警，>= 85% 严重 |
| 回源锁等待 P95 | < 500 ms |
| 缓存读取错误率 | > 1% 持续 5 分钟告警 |
| Stale 降级率 | > 10% 持续 10 分钟告警 |

## 10. 安全与观测

- Redis 使用私网、认证和 TLS（跨主机场景），不暴露公网。
- 缓存用户数据时缩短 TTL，并确保序列化内容不含凭据。
- 记录命中层级、Key 类别、耗时、数据年龄和降级原因，不记录完整 Key 中的用户标识。
- 监控连接数、命中率、淘汰、内存、锁冲突和序列化失败。
