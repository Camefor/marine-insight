# 部署文档

## 1. 部署范围

v1.0 生产部署包含 Blazor Web/API、PostgreSQL、可选 Redis、反向代理和观测采集。Worker 仅在启用预热、清理、重算、NOAA 文件处理或通知任务时独立部署。Open-Meteo、Stormglass、WorldTides、地图和 AI 为外部服务，不在本系统内托管。

## 2. 环境

| 环境 | 用途 | 数据/依赖 |
| --- | --- | --- |
| Local | 日常开发 | SQLite 或本地 PostgreSQL，模拟 Provider |
| Development | 联调 | PostgreSQL、可选 Redis、测试 API Key |
| Staging | 发布验证 | 与生产同拓扑，隔离数据库和 Provider 配额 |
| Production | 用户访问 | HTTPS、备份、监控、最小权限 Secret |

禁止开发、测试和生产共用数据库、Redis Namespace 或 Provider 密钥。

## 3. 基础设施要求

单实例初始建议：

| 资源 | 最低 | 建议 |
| --- | --- | --- |
| Web | 1 vCPU / 1 GB | 2 vCPU / 2 GB |
| PostgreSQL | 1 vCPU / 1 GB / 20 GB | 2 vCPU / 4 GB / 50 GB SSD |
| Redis | 128 MB | 256-512 MB |
| 系统 | Linux x64 | 受支持的 LTS 发行版 |

容量需根据地点数、168 小时点位保留、访问量和 Provider 限额调整，不能将以上数值视为固定生产容量。

| `ConnectionStrings__MarineInsight` | 是 | PostgreSQL 连接字符串 |
| `Redis__ConnectionString` | 是 | 可选 Redis 连接 |
| `Caching__Forecast__Environment` | 否 | 缓存环境隔离段，默认 `development`；生产应显式设置 |

| `Caching__Forecast__StaleIfErrorLifetime` | 否 | Provider 失败时允许旧批次降级的窗口，范围 0-24 小时，默认 2 小时 |

| `ForecastProviders__OpenMeteo__Timeout` | 否 | 单次 Provider 请求超时，默认 15 秒，范围 1-120 秒 |

敏感配置通过 Secret 注入，不写入仓库、镜像或日志。

### 4.1 WorldTides 密钥维护

- 本地直接运行 Web 时执行 `scripts/configure-worldtides-secret.ps1`。脚本隐藏输入并通过标准输入同时写入 `TideProviders:WorldTides:ApiKey` 和 `Enabled=true`，避免把明文 Key 放进命令历史；再次运行可轮换，使用 `-Disable` 可删除 Key 并关闭 Provider。User Secrets 依赖当前操作系统账户权限且并非加密生产密钥库，只适合开发机。
- 基础 `compose.yaml` 保持 WorldTides 关闭。需要潮汐时叠加 `compose.worldtides.yaml`，由 `MARINE_INSIGHT_WORLDTIDES_SECRET_FILE` 指向仓库外的受限文件；本地可使用已被 Git 和 Docker 构建上下文排除的 `.secrets/worldtides_api_key`。
- CI 和自动化测试默认使用固定契约样本，不注入真实 Key、不调用付费接口。只有受保护的手动 Staging 工作流才允许从平台 Secret 注入真实凭据。
- Staging 与 Production 使用不同 Key；密钥不得出现在命令输出、日志、截图、Issue、PR、测试快照或健康检查响应中。管理员页面只展示凭据是否存在。
- 轮换时先创建新 Key，更新 Secret 存储并重启 Web，验证一次真实潮汐查询和 Credit 状态后再吊销旧 Key。疑似泄露时立即吊销并检查供应商调用记录；不要只从 Git 删除文件后继续使用原 Key。

### 4.2 AI 解读密钥维护

- 本地直接运行 Web 时执行 `scripts/configure-ai-secret.ps1`。脚本隐藏输入并同时写入 `AI:ApiKey` 和 `Enabled=true`，避免明文 Key 进入命令历史；使用 `-Disable` 删除 Key 并关闭 Provider。AI 默认关闭，规则模板兜底，因此无 Key 不影响 P0 查询与分析。
- Docker 使用 Key-per-file 方式注入 `AI__ApiKey`（与 `AI__Enabled`、`AI__BaseUrl`、`AI__Model` 等环境变量搭配），密钥文件放在仓库外并限定读取权限。
- CI 和自动化测试默认不注入真实 Key，使用固定契约样本，避免消耗模型配额；只有受保护的手动 Staging 工作流才允许注入真实凭据。
- 疑似 Key 泄露时立即吊销并检查供应商用量记录；轮换时先创建新 Key、更新 Secret 并重启，验证一次真实解读后再吊销旧 Key。

## 5. 发布前检查

- 版本标签、变更日志和镜像摘要已确认。
- 单元、集成、E2E、算法黄金样本和安全扫描通过。
- Open-Meteo Weather/Marine 契约样本、时间轴合并和 Staging 实测通过；Stormglass/WorldTides 启用时已确认预算、配额和凭据。
- 数据库迁移 SQL 已评审并完成备份。
- 生产配置、Secret、域名、TLS 和反向代理已验证。
- 健康检查、日志、指标、告警和 Runbook 可用。
- 回滚镜像、数据库兼容策略和负责人已确认。

## 6. 标准部署流程

1. 构建并扫描不可变镜像，使用提交 SHA 和语义版本双标签。
2. 在 Staging 执行迁移、部署和完整冒烟测试。
3. 备份生产数据库，记录恢复点。
4. 使用独立迁移任务执行生产 EF Core 幂等 SQL。
5. 部署 Web/Worker，等待 `/health/ready` 通过。
6. 验证登录、地点搜索、实时/缓存查询、分析、降级和管理只读页。
7. 观察错误率、延迟、Provider 调用和数据质量至少 15-30 分钟。
8. 完成发布记录；异常达到回滚阈值时立即回滚。

## 7. 数据库迁移

- 迁移与应用版本一一记录，生产禁止开发机直接连接执行。
- 扩展列/表先部署兼容代码，再回填，最后在后续版本删除旧结构。
- 长时回填拆为后台批次，避免迁移事务长时间锁表。
- 应用运行账号不拥有 DDL 权限；迁移任务使用短期受限凭据。
- 回滚优先回滚应用，数据库使用向后兼容；破坏性迁移依赖备份恢复或专门反向脚本。

## 8. 健康检查

| 端点 | 检查 | 失败影响 |
| --- | --- | --- |
| `/health/live` | 进程和事件循环可用 | 重启容器 |
| `/health/ready` | 配置、数据库、已发布算法可用 | 停止接收流量 |
| `/health/dependencies` | Redis、Open-Meteo、Stormglass、WorldTides、AI 等摘要 | 告警；可降级依赖不一定下线 Web |

Open-Meteo、Stormglass、WorldTides 或 AI 的短时故障不应使存活检查失败。就绪策略需区分“基础分析不可用”和“付费增强/可选依赖异常”。

当前 Web 已提供 `/health/live` 和 `/health/ready`：存活检查不访问外部依赖，就绪检查以有界超时验证数据库连接，并只返回状态、检查名和耗时。Provider、Redis 和 AI 检查应在对应适配器完成后按可选依赖标签补充，不能把可降级依赖纳入存活检查。

## 9. 冒烟测试

- 首页/Dashboard 可加载，无控制台致命错误。
- 预置地点和坐标查询均返回数据或明确降级。
- 分析响应包含来源、时间、算法版本、置信度和免责声明。
- 构造缓存命中并确认 `fetchedAt` 未被刷新。
- 登录用户可增删收藏且不能访问其他用户资源。
- 管理员可查看 Provider 状态，但密钥不回显。
- `/health/live`、`/health/ready`、日志和 Trace 可用。

## 10. 回滚

触发条件示例：5xx > 5%、关键查询不可用、数据映射错误、评分规则严重回归、迁移异常或安全问题。

回滚步骤：

1. 停止新版本流量和后台重算任务。
2. 切回上一不可变镜像和兼容配置。
3. 验证就绪和核心冒烟场景。
4. 若数据结构不兼容，按已评审方案恢复备份或执行反向迁移。
5. 记录事件时间线、影响、Trace 和后续修复。

算法版本问题优先通过发布上一算法版本回滚，不需要回滚整个应用。

## 11. 运维

日常检查包括：API 成功率/P95、Provider 配额和错误、缓存命中、Stale 比例、数据质量、Unknown 分析比例、数据库容量/备份、证书有效期和安全事件。

每季度至少执行一次数据库恢复演练、Secret 轮换演练和 Provider 故障降级演练。

`MI-0027` 已提供以下可执行交付物：根目录 `Dockerfile`、`compose.yaml`、`deploy/Caddyfile`、Key-per-file Secret 模板、PostgreSQL 专用迁移项目，以及 `scripts/generate-migration-sql.ps1`、`backup-postgres.ps1`、`restore-postgres.ps1` 和 `smoke-test.ps1`。Web 的 `--migrate` 模式仅执行迁移后退出；反向代理只信任 Compose 固定代理 IP 的单跳 `X-Forwarded-*`。恢复脚本要求 `-ConfirmRestore`，停止 Web 后执行 `pg_restore --clean --if-exists` 并验证迁移历史。

当前环境缺少 Docker CLI，尚未执行真实 Compose 构建、PostgreSQL 迁移、备份恢复和代理 WebSocket 演练；这些是发布前必须在 Staging 完成的剩余准出项。
